# Errors and Validation

This document defines how all errors and input validation are handled in this project. Two rules are non-negotiable:

1. **Users never see technical details.** No error messages, stack traces, Mongoose errors, or internal state leak to the UI. Every visible message is written by the application, not generated by a library or runtime.
2. **All validation uses Zod.** Schemas are defined once and reused across Server Actions, Route Handlers, and client-side pre-validation.

---

## Error Taxonomy

| Type | What it is | Handling |
|---|---|---|
| **Validation error** | Input fails a Zod schema | Return field errors as a typed value; render inline via HeroUI `isInvalid` + `errorMessage` |
| **Expected error** | Predictable failure (auth, not found, conflict) | Return a typed error value; render via HeroUI `Alert` |
| **Unexpected error** | Bug, DB outage, unhandled exception | Throw; caught by `error.tsx` boundary; log internally |
| **Not found** | Resource does not exist | Call `notFound()`; render via `not-found.tsx` |
| **Global crash** | Root layout throws | Caught by `global-error.tsx` |

## Zod Schemas

### Location

All schemas live in `lib/schemas/`. Each file is named after the resource it validates.

```
lib/
  schemas/
    expense.ts
    category.ts
    auth.ts
```

### Writing schemas

Define schemas as named exports. Infer the TypeScript type alongside the schema — never write the type by hand.

```ts
// lib/schemas/expense.ts
import { z } from 'zod'

export const expenseSchema = z.object({
  amount: z
    .number({ invalid_type_error: 'Amount must be a number' })
    .positive('Amount must be greater than zero')
    .multipleOf(0.01, 'Amount cannot have more than 2 decimal places'),
  categoryId: z
    .string({ required_error: 'Please select a category' })
    .min(1, 'Please select a category'),
  date: z
    .string({ required_error: 'Date is required' })
    .date('Invalid date format'),
  description: z.string().max(200, 'Description cannot exceed 200 characters').optional(),
  notes: z.string().max(1000, 'Notes cannot exceed 1000 characters').optional(),
})

export type ExpenseInput = z.infer<typeof expenseSchema>
```

```ts
// lib/schemas/auth.ts
import { z } from 'zod'

export const loginSchema = z.object({
  email: z
    .string({ required_error: 'Email is required' })
    .email('Enter a valid email address'),
  password: z
    .string({ required_error: 'Password is required' })
    .min(1, 'Password is required'),
})

export const registerSchema = z.object({
  name: z
    .string({ required_error: 'Name is required' })
    .min(2, 'Name must be at least 2 characters')
    .max(100, 'Name cannot exceed 100 characters'),
  email: z
    .string({ required_error: 'Email is required' })
    .email('Enter a valid email address'),
  password: z
    .string({ required_error: 'Password is required' })
    .min(8, 'Password must be at least 8 characters'),
  confirmPassword: z.string(),
}).refine(data => data.password === data.confirmPassword, {
  message: 'Passwords do not match',
  path: ['confirmPassword'],
})

export type LoginInput = z.infer<typeof loginSchema>
export type RegisterInput = z.infer<typeof registerSchema>
```

```ts
// lib/schemas/category.ts
import { z } from 'zod'

export const categorySchema = z.object({
  name: z
    .string({ required_error: 'Category name is required' })
    .min(1, 'Category name is required')
    .max(50, 'Category name cannot exceed 50 characters'),
})

export type CategoryInput = z.infer<typeof categorySchema>
```

### Error message rules

- Messages are written for users, not developers: "Please select a category" not "categoryId is required".
- Never expose field names from the database schema in messages.
- Keep messages short — one sentence.

## Typed Action Result

All Server Actions return a typed result object instead of throwing for expected errors. This is the shared type.

```ts
// lib/types/action-result.ts
export type FieldErrors<T> = Partial<Record<keyof T, string[]>>

export type ActionResult<T = unknown> =
  | { success: true; data?: T }
  | { success: false; error: string; fields?: FieldErrors<T> }
```

- `fields` carries per-field validation errors from Zod's `flatten().fieldErrors`
- `error` carries a single human-readable summary message
- Never include internal error details in either field

## Server Actions — Validation Pattern

Use `safeParse` (never `parse`) so validation failures return a value rather than throwing.
Use `useActionState` in the Client Component to receive and display the result.

### 1. The Server Action

```ts
// app/actions/expenses.ts
'use server'

import { getServerSession } from 'next-auth'
import { authOptions } from '@/lib/auth'
import { expenseSchema } from '@/lib/schemas/expense'
import type { ActionResult } from '@/lib/types/action-result'
import type { ExpenseInput } from '@/lib/schemas/expense'
import dbConnect from '@/lib/db'
import Expense from '@/lib/models/Expense'

export async function createExpense(
  _prevState: ActionResult<ExpenseInput>,
  formData: FormData
): Promise<ActionResult<ExpenseInput>> {
  const session = await getServerSession(authOptions)
  if (!session) return { success: false, error: 'You must be signed in.' }

  const raw = {
    amount:      Number(formData.get('amount')),
    categoryId:  formData.get('categoryId') as string,
    date:        formData.get('date') as string,
    description: formData.get('description') as string | undefined,
    notes:       formData.get('notes') as string | undefined,
  }

  const result = expenseSchema.safeParse(raw)

  if (!result.success) {
    return {
      success: false,
      error: 'Please fix the errors below.',
      fields: result.error.flatten().fieldErrors as ActionResult<ExpenseInput>['fields'],
    }
  }

  try {
    await dbConnect()
    await Expense.create({ ...result.data, userId: session.user.id })
    return { success: true }
  } catch {
    // Log internally here (e.g., Sentry) — never expose the caught error
    return { success: false, error: 'Unable to save the expense. Please try again.' }
  }
}
```

**Rules:**
- Always validate auth before parsing the form data.
- Use `safeParse`, never `parse`.
- The `catch` block returns a generic user message. The original error is logged, never forwarded.
- Return `{ success: true }` — never include internal data in `data` beyond what the client needs.

### 2. The Client Component Form

```tsx
// app/(app)/expenses/_components/ExpenseForm.tsx
'use client'

import { useActionState } from 'react'
import { Alert, Button, Input, Select, SelectItem, DateInput } from '@heroui/react'
import { createExpense } from '@/app/actions/expenses'
import type { ActionResult } from '@/lib/types/action-result'
import type { ExpenseInput } from '@/lib/schemas/expense'

const initialState: ActionResult<ExpenseInput> = { success: false, error: '' }

export function ExpenseForm({ categories }: { categories: Category[] }) {
  const [state, formAction, pending] = useActionState(createExpense, initialState)

  return (
    <form action={formAction} className="flex flex-col gap-4">
      {/* Form-level error — shown when success is false and error is non-empty */}
      {!state.success && state.error && (
        <Alert color="danger" title={state.error} />
      )}

      <Input
        name="amount"
        label="Amount"
        labelPlacement="outside"
        type="number"
        startContent="₹"
        variant="bordered"
        isRequired
        isInvalid={!!state.fields?.amount}
        errorMessage={state.fields?.amount?.[0]}
      />

      <Select
        name="categoryId"
        label="Category"
        labelPlacement="outside"
        variant="bordered"
        isRequired
        isInvalid={!!state.fields?.categoryId}
        errorMessage={state.fields?.categoryId?.[0]}
      >
        {categories.map(c => (
          <SelectItem key={c.id}>{c.name}</SelectItem>
        ))}
      </Select>

      <DateInput
        name="date"
        label="Date"
        labelPlacement="outside"
        variant="bordered"
        isRequired
        isInvalid={!!state.fields?.date}
        errorMessage={state.fields?.date?.[0]}
      />

      <Input
        name="description"
        label="Description"
        labelPlacement="outside"
        variant="bordered"
        isInvalid={!!state.fields?.description}
        errorMessage={state.fields?.description?.[0]}
      />

      <Button
        type="submit"
        color="primary"
        fullWidth
        isLoading={pending}
      >
        Save Expense
      </Button>
    </form>
  )
}
```

**Pattern:**
- `Alert color="danger"` for the form-level summary message (only rendered when `state.error` is non-empty)
- `isInvalid` + `errorMessage` on each `Input` / `Select` / `DateInput` for field-level errors
- `isLoading={pending}` on the submit `Button` — never show a separate spinner component

## HeroUI Alert — Usage Rules

`Alert` from `@heroui/alert` is the only component used for visible error and status messages outside of form fields.

### Import

```ts
import { Alert } from '@heroui/react'
// or direct:
import { Alert } from '@heroui/alert'
```

### Color mapping

| Situation | `color` prop |
|---|---|
| Action failed (form error, save failed) | `"danger"` |
| Destructive action warning | `"warning"` |
| Success confirmation (inline, non-toast) | `"success"` |
| Informational notice | `"default"` |

### Usage in forms (action-level error)

```tsx
{!state.success && state.error && (
  <Alert color="danger" title={state.error} />
)}
```

### Usage in pages (data-fetch failure)

```tsx
// In a Server Component when a fetch returns no usable data
if (!expenses) {
  return (
    <Alert
      color="danger"
      title="Could not load expenses"
      description="Please refresh the page. If the problem persists, try again later."
    />
  )
}
```

### Usage in error.tsx boundaries

```tsx
// app/(app)/expenses/error.tsx
'use client'

import { Alert, Button } from '@heroui/react'

export default function ExpensesError({
  error,
  unstable_retry,
}: {
  error: Error & { digest?: string }
  unstable_retry: () => void
}) {
  return (
    <div className="flex flex-col gap-4 p-6">
      <Alert
        color="danger"
        title="Something went wrong"
        description="We couldn't load this page. You can try again or come back later."
      />
      <Button variant="bordered" onPress={unstable_retry} className="self-start">
        Try again
      </Button>
    </div>
  )
}
```

**Rules:**
- Never pass `error.message` or any runtime error text into `title` or `description`.
- Never render `error.stack`, `error.digest`, or any internal identifier in the UI.
- `error.digest` may be logged internally to correlate with server logs — it must not be displayed.

## Route Handlers — Validation Pattern

Route Handlers follow the same Zod-first approach. Return structured JSON with HTTP status codes. Never return stack traces or library error messages.

```ts
// app/api/expenses/route.ts
import { NextRequest, NextResponse } from 'next/server'
import { getServerSession } from 'next-auth'
import { authOptions } from '@/lib/auth'
import { expenseSchema } from '@/lib/schemas/expense'
import dbConnect from '@/lib/db'
import Expense from '@/lib/models/Expense'

export async function POST(req: NextRequest) {
  const session = await getServerSession(authOptions)
  if (!session) {
    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
  }

  let body: unknown
  try {
    body = await req.json()
  } catch {
    return NextResponse.json({ error: 'Invalid request body' }, { status: 400 })
  }

  const result = expenseSchema.safeParse(body)
  if (!result.success) {
    return NextResponse.json(
      { error: 'Validation failed', fields: result.error.flatten().fieldErrors },
      { status: 422 }
    )
  }

  try {
    await dbConnect()
    const expense = await Expense.create({ ...result.data, userId: session.user.id })
    return NextResponse.json(expense, { status: 201 })
  } catch {
    // Log internally
    return NextResponse.json(
      { error: 'Unable to save expense. Please try again.' },
      { status: 500 }
    )
  }
}
```

### HTTP status code convention

| Situation | Status |
|---|---|
| Unauthenticated | `401` |
| Authenticated but not owner | `403` |
| Validation failed | `422` |
| Resource not found | `404` |
| Conflict (duplicate email, etc.) | `409` |
| Unhandled server error | `500` |

## Not-Found Handling

Call `notFound()` when a resource the user requested does not exist. Never return a null-state page or a generic error.

```ts
// app/(app)/expenses/[id]/page.tsx
import { notFound } from 'next/navigation'
import { getServerSession } from 'next-auth'
import { authOptions } from '@/lib/auth'
import Expense from '@/lib/models/Expense'

export default async function ExpensePage({ params }: { params: { id: string } }) {
  const session = await getServerSession(authOptions)
  const expense = await Expense.findOne({ _id: params.id, userId: session!.user.id }).lean()

  if (!expense) notFound()

  return <ExpenseDetail expense={expense} />
}
```

```tsx
// app/(app)/expenses/[id]/not-found.tsx

        Back to expenses
      </Button>
    </div>
  )
}
```

## Error Boundary Files

### Segment-level — `error.tsx`

Place `error.tsx` alongside any `page.tsx` that fetches data. Must be a Client Component.

```tsx
// app/(app)/dashboard/error.tsx
'use client'

import { useEffect } from 'react'
import { Alert, Button } from '@heroui/react'

export default function DashboardError({
  error,
  unstable_retry,
}: {
  error: Error & { digest?: string }
  unstable_retry: () => void
}) {
  useEffect(() => {
    // Replace with your logging service (e.g. Sentry.captureException(error))
    console.error('[DashboardError]', error.digest)
  }, [error])

  return (
    <div className="flex flex-col gap-4 p-6">
      <Alert
        color="danger"
        title="Something went wrong"
        description="We couldn't load the dashboard. Please try again."
      />
      <Button variant="bordered" onPress={unstable_retry} className="self-start">
        Try again
      </Button>
    </div>
  )
}
```

### Global fallback — `app/global-error.tsx`

Catches errors that escape the root layout. Must include its own `<html>` and `<body>` tags.

```tsx
// app/global-error.tsx
'use client'

import { useEffect } from 'react'
import { HeroUIProvider, Alert, Button } from '@heroui/react'

export default function GlobalError({
  error,
  unstable_retry,
}: {
  error: Error & { digest?: string }
  unstable_retry: () => void
}) {
  useEffect(() => {
    console.error('[GlobalError]', error.digest)
  }, [error])

  return (
    <html lang="en">
      <body>
        <HeroUIProvider>
          <div className="min-h-screen flex items-center justify-center p-6">
            <div className="flex flex-col gap-4 max-w-md w-full">
              <Alert
                color="danger"
                title="Application error"
                description="An unexpected error occurred. Please refresh the page."
              />
              <Button variant="bordered" onPress={unstable_retry}>
                Refresh
              </Button>
            </div>
          </div>
        </HeroUIProvider>
      </body>
    </html>
  )
}
```

## Toast Notifications

Use HeroUI's toast system for transient feedback after async actions (successful save, delete, etc.). Toasts are non-blocking and dismiss automatically.

```tsx
// Wherever the action result is consumed in a Client Component
import { addToast } from '@heroui/toast'

async function handleDelete(id: string) {
  const result = await deleteExpense(id)
  if (result.success) {
    addToast({ title: 'Expense deleted', color: 'success' })
  } else {
    addToast({ title: result.error, color: 'danger' })
  }
}
```

### Toast vs. Alert

| Use `addToast` | Use `Alert` |
|---|---|
| Action completed successfully | Form submission failed |
| Record deleted | Page-level data fetch failed |
| Settings saved | Inline warning that persists until resolved |
| Transient confirmation | Error that requires user attention before continuing |

## Error Logging

Log errors before returning generic messages to users. Never log request body contents that may contain PII.

```ts
// Minimal pattern until a logging service is configured
function logError(context: string, error: unknown) {
  if (process.env.NODE_ENV === 'production') {
    // Replace with: Sentry.captureException(error, { extra: { context } })
    console.error(`[${context}]`, error instanceof Error ? error.message : error)
  } else {
    console.error(`[${context}]`, error)
  }
}
```

Usage in a catch block:

```ts
} catch (error) {
  logError('createExpense', error)
  return { success: false, error: 'Unable to save the expense. Please try again.' }
}
```

## Client-Side Pre-validation (Optional)

Client-side validation with Zod can be layered on top of server validation to give instant feedback before a form is submitted. It is an enhancement — server validation is always the source of truth.

Use the same schema that the Server Action uses.

```tsx
'use client'

import { expenseSchema } from '@/lib/schemas/expense'

function validateAmount(value: string) {
  const result = expenseSchema.shape.amount.safeParse(Number(value))
  return result.success ? null : result.error.errors[0].message
}

// In the Input component:
<Input
  name="amount"
  onBlur={e => setAmountError(validateAmount(e.target.value))}
  isInvalid={!!amountError}
  errorMessage={amountError}
/>
```

Never skip server-side validation because client-side validation passed — they serve different purposes.

## What Never to Do

| Forbidden | Why |
|---|---|
| `<Alert title={error.message} />` | Exposes library/runtime internals |
| `<p>{err.stack}</p>` | Exposes stack trace to users |
| `return { error: mongooseError.message }` | Exposes DB schema details |
| `catch (e) { throw e }` in a Server Action | Bypasses the user-friendly error layer |
| `schema.parse(data)` in a Server Action | Throws a ZodError that surfaces as an unhandled exception |
| Returning `userId` or `_id` from a failed action | Unnecessary data exposure |
| Generic `"Something went wrong"` with no retry path | Leaves the user stuck — always pair with a recovery action |

---

## Checklist for Every Form or Mutation

1. Schema defined in `lib/schemas/` using Zod
2. Server Action uses `safeParse` and returns `ActionResult<T>`
3. Auth check runs before validation
4. `catch` block logs internally and returns a generic user message
5. Client Component uses `useActionState` to receive the result
6. `Alert color="danger"` renders `state.error` when `!state.success`
7. Each field has `isInvalid` and `errorMessage` wired to `state.fields`
8. Submit `Button` has `isLoading={pending}`
9. Success path uses `addToast` or redirects — never leaves the form in an ambiguous state
